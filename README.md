# ExpiryMate 软件需求说明书

> 版本：1.1（Markdown 基线）  
> 日期：2026-10-09  
> 项目：ExpiryMate 物品保质期管理系统  
> 架构：前后端分离；PC Web 优先，响应式兼容手机

## 1. 文档目的

本文定义 ExpiryMate 第一阶段 Web 产品的产品范围、功能需求、数据规则、前后端接口、技术方案和验收条件，供产品、前端、后端和测试人员共同使用。技术选型是本项目的推荐实施基线；具体依赖版本应在项目初始化时选取仍受支持且互相兼容的稳定版本。

## 2. 项目目标与范围

ExpiryMate 帮助用户记录物品的生产日期、购买日期、保质期和到期日，集中查看物品状态，并在临期时生成提醒。

### 2.1 第一阶段包含

- 用户注册、登录、退出；每位用户只能访问自己的数据。
- 物品新增、详情、编辑、删除和已用完/已处理标记。
- 生产日期、购买日期、保质期、包装标注到期日录入。
- 总览统计、清单、搜索、分类和状态筛选、到期日期排序、分页。
- 用户配置临期阈值和提醒提前天数。
- 站内通知和后台定时提醒任务；授权且支持的浏览器可启用 Web Push。
- PC 优先界面，并采用响应式布局支持手机浏览器。

### 2.2 后续再评估

条码商品查询、OCR/照片识别、家庭共享、邮件/短信、复杂库存分析、原生 iOS/Android 应用。手动录入和到期提醒不依赖商品信息 API；Web Push 使用浏览器推送能力，不要求接入商品数据 API。

## 3. 用户与使用场景

| 角色 | 目标 | 操作 |
|---|---|---|
| 注册用户 | 管理自己的物品和提醒 | 登录、录入物品、浏览清单、查看通知、处理或修改记录 |
| 提醒任务 | 发现达到提醒条件的物品 | 按用户时区扫描、生成去重通知、尝试推送 |
| 运维人员 | 确保服务可用 | 查看健康状态、任务执行结果和错误日志；不以运维身份浏览用户业务数据 |

典型流程：用户录入包装信息；系统确定到期日并显示状态；后台任务按用户设置生成提醒；用户打开站内提醒或收到浏览器通知后，查看物品并标记处理。

## 4. 功能需求

优先级：P0 为首发必须；P1 为首发增强；P2 为后续版本。

| 编号 | 需求 | 优先级 | 验收条件 |
|---|---|---|---|
| FR-001 | 注册、登录、退出和身份验证 | P0 | 未认证用户不能读取或修改物品；数据按用户隔离 |
| FR-002 | 新增物品，支持名称、生产日期、购买日期、保质期或到期日 | P0 | 表单校验清晰；可直接填到期日，也可由生产日期和保质期计算 |
| FR-003 | 查看、编辑和删除自己的物品 | P0 | 保存后清单和详情一致；删除有确认或软删除规则 |
| FR-004 | 根据到期日显示剩余天数和状态 | P0 | 状态按用户本地自然日计算；到期当天显示“今日到期” |
| FR-005 | 总览显示物品总数、临期数、过期数和近期到期物品 | P0 | 统计与对应清单筛选一致 |
| FR-006 | 搜索、分类/位置/状态筛选、排序和分页 | P0 | 支持组合筛选、清空条件和无结果提示 |
| FR-007 | 设置临期阈值、提醒开关和提前天数 | P0 | 保存后生效；阈值变化会重新计算未发送提醒 |
| FR-008 | 站内通知中心 | P0 | 显示物品、原因、到期日和提醒状态；可标记已读/已处理 |
| FR-009 | 已用完、已丢弃或已处理标记 | P1 | 处理后的物品不再产生新提醒 |
| FR-010 | 数量、单位、分类、存放位置、备注、开封日期 | P1 | 均可选填；未填写不妨碍保存 |
| FR-011 | 浏览器 Web Push | P1 | 用户授权且浏览器支持时发送；拒绝授权不影响站内通知 |
| FR-012 | 导出个人数据 | P2 | 后续确定格式和字段范围 |

## 5. 业务规则

1. 用户直接填写包装到期日时，该日期为状态计算的权威值。若同时填写生产日期和保质期，系统提示核对，不静默覆盖。
2. 未直接填写到期日时，以生产日期加保质期计算。单位支持天、月、年；月末无对应日期时取目标月份最后一天。
3. 状态定义：`expires_on < 用户本地 today` 为已过期；`today ≤ expires_on ≤ today + 临期阈值` 为即将到期；其余为正常。到期日当天仍属于临期。
4. 建议默认提醒点为到期前 7 天、3 天、1 天和当天；用户可更改。最终默认配置可在产品确认后调整。
5. 同一用户、同一物品、同一规则和同一触发日只生成一条通知。Worker 重复执行不得造成重复提醒。
6. 已用完、已丢弃或已删除物品不再生成新提醒。到期日变更后，未发送的旧计划应重新计算。
7. 用户关闭浏览器推送时，后台仍保存站内通知。推送失败不得导致站内提醒丢失。
8. 日期字段使用 `YYYY-MM-DD` 日期值，避免因服务器时区转换造成日期偏移。用户时区用于提醒触发时间和展示。

## 6. 数据需求

| 实体 | 核心字段 | 说明 |
|---|---|---|
| User | id、login_id/email、password_hash、timezone、created_at | 密码只保存安全哈希；用户时区用于日期展示和提醒 |
| Item | id、user_id、name、category、location、quantity、unit、manufactured_on、purchased_on、shelf_life_value、shelf_life_unit、expires_on、opened_on、notes、status、created_at、updated_at、deleted_at | `expires_on` 为状态判断权威日期 |
| ReminderPreference | user_id、enabled、remind_before_days、preferred_time、channels | 一用户一组偏好；可支持多个提前天数 |
| Notification | id、user_id、item_id、rule_key、scheduled_for、sent_at、read_at、status、dedupe_key | `dedupe_key` 唯一约束，避免重复提醒 |
| PushSubscription | id、user_id、endpoint、keys、created_at、revoked_at | 仅启用 Web Push 后使用；订阅密钥需要保护 |

校验要求：物品名称必填；数量大于 0；生产、购买和开封日期关系合理；到期日必须直接提供或可计算。已保存数据的更新要验证用户拥有该资源。

## 7. 前后端分离架构

```text
浏览器（React Web / PWA）
          │ HTTPS + JSON REST API
          ▼
Spring Boot API ───── PostgreSQL
          │
          └──── Scheduler / Reminder Worker ── 站内通知 / Web Push
```

- 前端通过版本化 API 读写数据，不直接连接数据库。
- 后端负责身份验证、授权、业务校验、到期状态、提醒生成、去重和持久化。
- 定时任务按用户时区扫描临期物品并生成通知；在初期无需单独引入消息队列。
- 后端 API 和提醒 Worker 可先作为同一个 Spring Boot 部署中的不同模块/任务运行；负载增加后再独立扩展。

## 8. 推荐技术栈及用途

| 层 | 推荐技术 | 用途与理由 |
|---|---|---|
| 前端语言 | TypeScript | 为页面、表单和 API 数据定义类型，减少字段不一致问题 |
| 前端框架 | React | 组件化构建总览、清单、物品表单和通知界面；使用官方 React DOM Web APIs |
| 构建工具 | Vite | 前端开发服务器和生产构建；开发体验轻量，前后端可独立构建部署 |
| UI 组件 | Ant Design（建议） | 提供表格、表单、日期选择器、筛选和分页组件，适合 PC 管理界面；品牌视觉可通过主题变量调整 |
| 路由和请求 | React Router + Fetch API | 页面路由；Fetch 调用 REST API，封装统一错误处理和身份状态 |
| 后端语言 | Java LTS 版本 | 生态成熟，适合持续维护 API 和后台任务 |
| 后端框架 | Spring Boot + Spring Web | 提供独立运行的 Java API 服务、REST 接口和健康检查能力 |
| 安全 | Spring Security | 认证、授权和接口安全控制；服务端必须验证资源所有权 |
| 数据访问 | Spring Data JPA | 将用户、物品和通知实体映射到关系数据库；复杂查询使用显式 Repository 查询 |
| 数据库 | PostgreSQL | 持久保存用户、物品、提醒偏好和通知；使用事务、索引和唯一约束维护一致性 |
| 数据库迁移 | Flyway | 版本化管理数据库结构变化，使本地、测试和生产结构可重复更新 |
| 接口契约 | OpenAPI 3 | 描述 REST API 请求、响应、校验和错误结构；前后端据此协同开发 |
| 定时任务 | Spring Scheduling | MVP 阶段周期性扫描并生成提醒，不先引入 Redis 或消息队列 |
| Web Push | Service Worker + Push API + VAPID | 浏览器授权后推送提醒；浏览器/设备支持情况受平台策略影响，站内提醒始终保留 |
| 部署 | Docker + Docker Compose（开发/小规模部署） | 统一运行前端、后端和 PostgreSQL；生产环境按实际平台拆分服务和密钥管理 |
| 测试 | JUnit 5 / Spring Boot Test；Vitest / Testing Library；Playwright（端到端） | 后端规则和 API、前端组件交互、关键用户流程分别验证 |

### 8.1 技术选型边界

以上是建议基线，不表示项目已经安装或配置这些组件。第一阶段不需要商品信息 API、OCR API、Redis、Kafka 或微服务。若后续要支持商品扫码查询，再单独评估商品数据库覆盖率、费用和 API 授权；若提醒规模或可靠性要求增长，再评估消息队列。

### 8.2 版本策略

不在需求说明书中固定框架小版本。项目初始化时选择各官方支持周期内的稳定版本，并检查 Java、Spring Boot、数据库驱动、前端构建工具之间的兼容矩阵；依赖版本锁定在构建文件中，升级需经过测试。

## 9. API 约定

- 基础路径：`/api/v1`；HTTPS；JSON 请求与响应。
- 日期：`YYYY-MM-DD`；时间戳：ISO 8601 UTC。
- 错误响应统一包含错误代码、用户可读消息和字段级校验详情。
- 列表支持 `page`、`page_size`、`sort_by`、`sort_order`、`status`、`category`、`q`；限制最大分页数量。
- 服务端对每个对象执行所有者校验；不能只靠前端隐藏按钮控制权限。
- OpenAPI 契约与实现保持同步；创建提醒具备幂等和去重策略。

| 方法 | 路径 | 用途 |
|---|---|---|
| POST | `/api/v1/auth/register` | 注册 |
| POST | `/api/v1/auth/login` | 登录 |
| GET | `/api/v1/dashboard/summary` | 首页汇总 |
| GET / POST | `/api/v1/items` | 分页查询 / 新建物品 |
| GET / PATCH / DELETE | `/api/v1/items/{itemId}` | 详情 / 更新 / 删除 |
| GET | `/api/v1/notifications` | 查询站内通知 |
| PATCH | `/api/v1/notifications/{notificationId}` | 标记已读或处理 |
| GET / PUT | `/api/v1/settings/reminders` | 查询或更新提醒偏好 |
| POST / DELETE | `/api/v1/push-subscriptions` | 创建或撤销浏览器推送订阅 |

## 10. 非功能需求

- **易用性：** PC 为主要界面；核心页面不需横向滚动；手机可完成新增、查看和处理。状态不能只依赖颜色表达。
- **性能：** 在目标部署环境和常规数据规模下，列表/详情 API P95 目标不超过 500 ms（不含网络传输）；汇总接口避免对每条物品逐条请求。
- **可靠性：** 提醒任务支持有限重试；任务重复运行可安全去重；记录失败原因。
- **安全：** 全站 HTTPS；密码哈希；后端对象级授权；限制暴力登录；日志不记录密码、令牌和完整推送密钥。
- **可维护性：** 前后端独立构建；接口版本化；业务规则集中在服务层；数据库变更纳入迁移脚本。
- **备份：** 上线前确定生产数据备份频率、恢复目标并演练恢复流程。
- **兼容性：** 首发浏览器版本范围由部署和发布计划冻结；响应式目标覆盖主流手机浏览器。

## 11. 验收标准

| 编号 | 场景 | 通过条件 |
|---|---|---|
| AT-01 | 生产日期加保质期 | 普通日期、跨月、闰年和月末计算符合规则 |
| AT-02 | 直接输入包装到期日 | 保存、编辑、详情和清单均以该日期显示和判断状态 |
| AT-03 | 到期状态边界 | 昨日、今日、阈值最后一天和阈值外一天显示正确 |
| AT-04 | 多用户隔离 | 用户不能通过修改 URL 或 API ID 访问他人数据 |
| AT-05 | 清单操作 | 搜索、筛选、排序、分页组合结果正确 |
| AT-06 | 重复任务 | 同一提醒任务重复运行不生成重复通知 |
| AT-07 | 用户关闭 Web Push | 站内通知仍正常生成和查看 |
| AT-08 | 手机窄屏 | 可完成新增、详情查看和处理，关键操作可见可达 |

## 12. 开发流程建议

1. **需求与原型：** 确认提醒默认值、字段必填规则、页面流程和本文件中的待决事项。
2. **仓库与基础设施：** 建立 `frontend/`、`backend/`、`ExpiryMate-doc/`；配置本地容器、开发环境变量和代码检查。
3. **接口与数据：** 先定 OpenAPI、实体关系、日期计算和错误码，再并行实现前后端。
4. **MVP 闭环：** 注册登录 → 物品 CRUD → 日期和状态 → 总览/清单 → 站内提醒。
5. **提醒增强：** 定时任务去重、失败重试、用户偏好，再接 Web Push。
6. **验收与发布：** 覆盖本文件 AT-01 至 AT-08，验证备份恢复、安全和手机布局。
7. **试用扩展：** 收集使用反馈后评估扫码、OCR、共享和原生 App。

建议项目目录：

```text
ExpiryMate/
├─ frontend/          # React + TypeScript + Vite
├─ backend/           # Java + Spring Boot
├─ deploy/            # Docker Compose、环境配置模板
└─ ExpiryMate-doc/    # SRS、OpenAPI 导出和设计文档
```

## 13. 待确认事项

- 临期阈值和默认提前提醒天数（当前建议 7、3、1、0 天）。
- 首发 Web Push 是否列为必须；推荐先保证站内通知，再加入授权推送。
- 物品删除采用软删除或永久删除，以及通知和历史数据保留期限。
- 是否需要邮箱验证、密码找回以及注册防滥用策略。
- 目标生产部署平台、域名、备份频率和服务可用性目标。
- 最终分类、单位清单和浏览器版本支持范围。
